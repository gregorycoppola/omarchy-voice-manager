Different ways to listen.

Finding accurate voice control with low latency and low user cost. Compare local and cloud pipelines, then test how training changes the tradeoffs.

The research question

How much latency and cost can we remove while preserving—or improving—the accuracy of speech-to-intent?

The voice managers below are architectural reference points. Our experiment compares interchangeable recognition and intent components, including smaller models trained for this task. Today’s off-the-shelf accuracy is a baseline, not a permanent limit.

Model the latency

Measure each stage and the full response path. Compare local, hybrid, cloud, and integrated audio-to-intent designs on the same commands and hardware.

Track user cost

Record API usage, local memory and compute, and retries. Keep recurring operation costs separate from the one-time cost of training and deployment.

Improve the models

Test whether task-specific training makes a smaller, faster model accurate enough to compete with a larger model. Treat the improvement as a hypothesis to measure.

Research objective: find configurations where no tested alternative improves accuracy, latency, and cost together. Choose among those tradeoffs for the user; do not collapse them into an arbitrary single score.

A latency model for every pipeline

The primary clock starts at the last spoken sound and ends when a validated intent is ready. A second clock ends when the visible action completes. Track time until first feedback separately: a quick acknowledgement is not a completed command.

Are speech recognition and intent classification combined?

Separate stages: a recognizer produces text, then a classifier turns that text into an action and arguments. If those stages run sequentially, their actual durations add. The chart’s stacked view illustrates this using our existing component medians.

Integrated model: a speech-capable model can produce the action directly from audio. We measure one audio-to-intent span when separate internal timings are unavailable. There is still one resulting intent; it is the processing stages that are combined.

Streaming: work can happen while you speak, and stages can overlap. A stacked sum cannot represent that elapsed wait reliably. We will plot measured time from speech end to intent readiness as a joint bar, with an event timeline when stage details are available.

Experiment matrix and reporting rules

Compare local ASR + rules, local ASR + local classifier, local ASR + cloud classifier, cloud ASR + local classifier, cloud ASR + cloud classifier, and integrated cloud audio-to-intent. Use the same supported intents and target context. Replay streaming audio at speaking speed.

Report median and p95 from end-to-end samples, cold startup separately from warm sessions, and sample counts. Do not sum component medians or p95 values and label the result a measured system percentile. Repeat under representative load and network conditions. Report failures and timeouts alongside successful latency; retain them in the study.

What would it cost?

Local speech recognition has no API fee, whichever local recognizer we choose. Hosted intent services charge only for the cloud portion. These are USD estimates from published rates, not observed bills; accuracy is not modeled.

Two different options: a local Jev-style classifier such as Kev has zero API fees. TypeSafe’s hosted Jev API is a paid cloud classifier. Both are listed below so we can compare local and hosted decisions.

Text input includes instructions, tool schemas, transcript where used, and retained context billed on each attempt. Defaults are illustrative, not token measurements. Extra attempts are a workload assumption, not an inferred error rate. All attempts are modeled with the same average size.

Training is part of the experiment

Working hypothesis: a smaller model adapted to our command domain can move the accuracy–latency–cost tradeoff in our favor. Measure baseline and trained variants together; keep larger models as reference points.

Recognition track

Build reviewed audio/transcript pairs covering app names, numbers, negation, accents, and background noise. Compare vocabulary hints or contextual biasing with acoustic-model adaptation where the chosen model supports training.

Evaluate word error rate and command-critical transcription errors separately. Check the final intent as well: fewer word errors do not automatically mean fewer wrong actions.

Intent track

Train on text → structured intent examples, including arguments, unsupported requests, and ambiguity. Include independently labeled ASR-error examples so the classifier encounters realistic recognition output.

Compare prompting-only baselines, supervised fine-tuning or LoRA, and possible distillation from a stronger model. Review generated labels; the teacher is not the ground truth.

What makes a training result useful?

Split training, validation, and held-out tests by recording session and phrasing family before tuning. Include held-out speakers when claiming generalization to other users. Keep personal adaptation results distinct from general-user results.

Compare each trained model with its own untrained baseline using the same runtime, hardware, and quantization. Then vary quantization as a separate experiment. A smaller model is a candidate, not a promise of lower latency: measure it on the target device.

Report exact intent-and-argument accuracy, false actions, unnecessary rejections, clarification rate, latency, memory, and cost per attempted and correctly completed task. Account for repeated attempts and human correction time. Track training, labeling, and deployment costs separately and show the usage level at which savings could repay them.

Inside each project

Mechanisms, scope, and limitations

Recognition quality and intent quality are separate questions. A perfect transcript can still select the wrong action; a policy check does not prove the user's meaning was understood.

4 projects shown

Skipper

Local · grammar

A small, inspectable command language for the desktop.

Speech → words
Hold-to-talk records a short clip. Parakeet TDT 0.6B v3 runs locally through a community INT8 ONNX conversion and onnx-asr on the CPU. Recognition completes after release.
Words → intent
Finite grammar patterns and vocabulary generate phrases mapped to typed intents. Saved corrections and exact matches come before fuzzy matching. Eligible fuzzy candidates use SequenceMatcher; the best meaning needs at least 0.72 similarity and a 0.06 lead. Some commands require stricter matching.
Command coverage
Window selection, tiling, hide/restore, app launching, workspaces, selected browser destinations/tab routing, audio, brightness, media, and named actions. Explorer exposes grammar, intents, recordings, and corrections.
Customization & data
Saved speech corrections map a recognized phrase to a full intent. Named actions map exact custom phrases to existing typed actions. Recordings and history stay local. The optional browser connection reads tab metadata.
Interpretation example & limits

open <destination> with gmail produces open_destination(destination="gmail"). Fuzzy scores measure text resemblance, not semantic certainty. Corrections are lookup entries, not model training. General conversational requests, unrestricted scripts, and dictation into other apps are outside this reviewed command path.

Evidence: local development checkout, September 23, 2026 (0.2.0-dev; includes unreleased work).

Genesis

Local · optional agent

Broad desktop commands with user-defined routines.

Speech → words
Click-to-talk captures audio and delegates transcription to voxtype transcribe. The speech model is selected in Voxtype, rather than fixed by Genesis.
Words → intent
Normalizes text, then checks ordered Bash regular expressions and phrase rules. Built-ins precede custom commands. Custom matching uses phrase containment, longest phrase first. Emits action, arguments, label, and a confirmation flag as JSON.
Command coverage
Apps, audio, brightness, playback, power/session actions, screenshots, reminders, themes, workspaces, and status queries. Smart-home and TV commands delegate to other plugins. Custom commands and scheduled routines expand the catalog.
Customization & data
Custom phrases can call plugin IPC or scripts. Optional agent fallback handles unmatched requests when enabled; it is off by default in the reviewed parser and requires on-screen confirmation. Successful input recordings are deleted.
Interpretation example & limits

A phrase such as “turn off the TV” matches a TV rule before system power rules. Some other rules match substrings rather than the whole utterance, so negated sentences can still match. Confirmation limits execution but does not fix that interpretation. The reviewed executor relies on its caller for confirmation.

Omarvis

Cloud · conversation

A conversational assistant at the desk or on the phone.

Speech → words
Hotkey-started ElevenLabs voice sessions combine speech input, a conversational model, and spoken responses. Separate dictation captures speech and pastes the transcript into an application. The reviewed integration does not fix one local ASR model.
Words → intent
The LLM receives command catalogs and desktop context, then invokes a client run tool with a command string. Local code parses the command into arguments, checks allowed routes and flags, and decides run, confirm, or reject.
Command coverage
Apps, workspaces, themes, audio, brightness, screenshots, reminders, locking, Herdr coding-agent operations, and Chromium automation through agent-browser. Browser tools include tab references, navigation, clicks, and forms.
Customization & data
Catalogs expose supported command routes. Voice sessions send audio and desktop context to ElevenLabs; screenshots are available on request. Optional phone access uses Tailscale. Cloud provider usage requires an account and is billed.
Interpretation example & limits

For a workspace request, the model chooses an exact catalog command and supplies it to run. Execution uses an argument list rather than an unrestricted shell. Sensitive operations require a later confirmation of the exact pending command, with a 30-second window. Browser automation and dictation have separate paths and targeting behavior.

OMA

Cloud · tool calls

omarchy-voice: desktop tools and persistent tasks.

Speech → words
OpenAI handles speech through Realtime or an optional Live backend. This is a speech-capable model session, not necessarily a separate local transcript-first pipeline. A typed one-shot planner is also available.
Words → intent
The model receives instructions, capability context, and named tool schemas. It selects tools and generates structured arguments. A shared local executor applies policy checks. Live can delegate tasks to a backend model.
Command coverage
Apps, windows, workspaces, desktop settings, installed-capability discovery, browser/page reading, OCR interaction, tmux terminal reading and watches, notes/clipboard tools, durable coding or analysis tasks, and optional camera inspection.
Customization & data
Tool schemas and discovered capabilities define what is available. Background tasks can preserve state and artifacts for resumption. Audio goes to OpenAI while listening; task-dependent page text, images, and tool results can also be sent. API usage is billed.
Interpretation example & limits

“Tell me when the build finishes” can lead to a terminal watch instead of a single desktop action. The reviewed watch detects terminal activity transitions; idle alone does not prove a successful exit. Browser workers are bounded model-driven tasks. Its dry-run mode still allows read-only queries and API calls.
